The current situation:

- `crete-design-package` already follows your proposed approach.
- Specification management has an independent core, mixed with HAI configuration and integration.
- Most other skills require HAI Activities, conventions, saved settings or runtime helpers.
- Role authoring, workflow authoring, framework advice and release management contain substantial HAI-specific knowledge. They need deliberate separation of reusable methods from HAI instructions.

The previous implementation enabled skills to run **without selecting a role**. It did not make them independent of HAI. Your observation identifies a real remaining architectural issue.

I recommend these boundaries:

| Component | What belongs there |
|---|---|
| **Skill** | Reusable method, input/output expectations, templates, scripts and genuine prerequisites. |
| **Role** | Responsibilities, authority, skill selection and HAI-specific usage: conventions, configuration, locations and handoffs. |
| **Workflow** | Order of work, responsible roles, artifact transfers, conditions, loops and human approvals. |
| **HAI framework** | Activity lifecycle, recording, persistence, configuration validation and workflow execution. |

For example, a requirements-analysis skill should know how to clarify a request. The Business analyst role should supply HAI context and expected deliverables. The framework should save the records; the workflow should decide what happens next.

This broadly matches the distinction between task-specific skills, specialist roles, persistent project instructions and tools described in [GitHub’s customization guidance](https://docs.github.com/en/copilot/concepts/customizations/comparing-customizations). The [Agent Skills specification](https://agentskills.io/specification) supports portable packages with declared dependencies, although it also permits product-specific skills.

**The benefits are worthwhile:** easier external skill adoption, reuse outside HAI, fewer dependencies on HAI’s folder structure, and simpler upstream updates. The main risk is moving duplicated HAI instructions into every role. Shared operational rules should remain in the framework.

There is one limit to the copy-and-paste expectation: a portable skill can still require Python, Git, particular tools or service access. HAI must also discover its folder and support its metadata. The current parser and installation behavior have interoperability limitations, documented in the review.

I recommend agreeing on these boundaries, then demonstrating them with one simple skill, one script-bearing skill and one external skill before changing the entire library.

**I would keep these roles and skills optional, but include them automatically in the standard HAI setup.** Users should not have to install them individually for a normal installation.

The key distinction is between a capability HAI must provide and a specialist that helps people use it:

| Capability | Where it belongs |
|---|---|
| Define the role and workflow formats | Core `.hai/` |
| Validate, install and register packages | Core `.hai/` |
| Execute workflows and maintain their state | Core `.hai/` |
| Help a person design a good role or workflow | Authoring roles and skills |

The core already provides much of the first group. The prefixed roles and skills provide the second: specialist instructions for creating and reviewing definitions.

**They are useful in most workspaces, but they are not necessary in every workspace.** An installation may only execute established workflows and use existing roles. It might never author either. HAI should also remain capable of installing its first role without needing a role-definition manager already installed.

Moving all authoring instructions into the core would make them mandatory framework material, increase the core’s maintenance scope, and make independent updates or replacements harder. Their HAI-specific nature alone does not make them core functionality.

Your concern about repeated installation is valid, though. I recommend solving it through installation defaults:

- **Standard setup:** automatically install and register both administration roles and their skills.
- **Minimal setup:** install the core alone; add authoring packages when needed.
- Keep one maintained source for each package and let installation create its environment copy.

This also makes ownership clearer: HAI maintains and distributes these packages, while a workspace can choose whether to use them or maintain a customized installed copy.

I would move an instruction into `.hai/` when **HAI requires it to function correctly regardless of which optional roles are installed**. I would retain instructions for producing good definitions in the authoring skills.

So my recommendation is: **make these standard included capabilities, rather than mandatory core components.** That gives new users a complete setup without making every installation carry the same specialists.
