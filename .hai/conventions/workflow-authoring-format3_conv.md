# Author configurable workflows

Use the shared workflow definition/run conventions as the format authority. Maintain historical format-2 definitions in their existing interpretation; never rewrite pinned historical run bytes. New portable processes use workflow_format 3. Reusable sources are optional explicitly selected definitions; installed definitions live in .hai_env/workflows/. A definition contains no environment destinations or execution state.

Before authoring, establish actual process authority, responsible roles, expected outcomes and artifact ownership. Steps name roles and expected results; the role chooses suitable available skills. Do not prescribe a workflow skill binding or duplicate skill methods. Missing capability is a dependency, not success.

Format 3 uses ordered Purpose, Locations, Inputs, Outcomes, Steps H2 sections. Locations has Name, Purpose, Contents columns and explains every required output base. Per-step Results adds Gate after Next; values are none or human. Each output location is configured:<location-name>/<step-id>-{execution}-<artifact-name>. The runtime adds a run UUID directory and fills execution with its per-step counter padded to at least three digits. No agent invents an execution number. Every authored result names actual output evidence; each result has a next step or ending and every graph node has a possible terminal route within bounded attempts.

Initial inputs use workspace:/activity: references. Step inputs use workflow:<input>, incoming:<output>, or accepted:<step>/<result>/<output>. Use feedback:<output> for the immediate predecessor historical change request/QA defects; it is not a live prerequisite binding for its older scope/design subtree. Result-specific accepted references distinguish QA passed evidence from defects. Declare every required earlier requirements/design/approval source on a partial return; do not rely on the immediately previous step to carry unrelated earlier artifacts. QA defects may describe an earlier implementation and remain explicitly bound to it. Use feedback:<output> for the exact immediate predecessor questions or defects: its immutable subtree is historical provenance with content integrity, while separately declared accepted requirements/design/approval retain recursive live freshness checks. Do not infer inputs from latest-looking filenames.

Human checkpoints use Gate human only on the result that actually requires approval/acceptance. Host presents current inputs, records the actual received natural-language human instruction verbatim, and submits a semantic attestation bound to the assignment checkpoint digest plus message ID/hash. The human need not echo a technical token. The runtime checks the existing typed human/received instruction after checkpoint preparation; host attribution is not independent identity authentication. Scope/design changes need fresh human approval; QA pass never substitutes for human acceptance. Final backlog work requires the existing owner's actual authority; no workflow automatically closes an Activity.

Installation preview must present each location's purpose/contents and request actual human-chosen workspace-relative bases. Installation apply requires all choices. Never invent live values, install by copying a source alone, or treat installation as run start. Config belongs separately in .hai_env/config/workflows/<name>.json. Ordinary reuse/update preserves human-selected locations. Unsafe paths, partial installations or incompatible contracts block without automatic repair. Use isolated labeled test choices when proving two environments.

Outputs resolve below <configured-base>/<run-uuid>/. Runtime-owned state, accepted copies/hashes, initial snapshots and exact input lineage remain below the owning Activity workflow-runs/<run-uuid>/. Canonical product outputs retain their existing owners; reports reference their actual changes, final names and checks. Intermediate files always retain the step/execution identity. Stable final names are an explicitly authorized product publication choice, never an automatic overwrite.

Review a normal path, failure/interruption, bounded QA return, missing/changed/unaccepted/superseded input, two human checkpoints and final completion handoff. Run pure workflow validate independently of role/skill/model readiness. Verify installation, configured paths and actual files through runtime fixtures. Test old format reads byte-preserving, two environments/runs, repeated steps, retained archival evidence and partial failure preservation. Structural validity is not semantic quality, human approval or successful execution.
