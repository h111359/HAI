## What

Define and implement distinct responsibilities for HAI roles, skills and workflows.
Document the principles as HAI concepts, reorganize the reusable source collections,
extract skills from existing roles, and provide an initial software-development
workflow with output locations configured for each installed environment.

The human currently authorizes backlog capture, clarification and review only. This item records
future implementation work. No folder rename, skill extraction, workflow installation
or runtime change is authorized by creating this item. The item remains pending
until the human reviews it and separately instructs how to proceed.

### 1. Concepts and responsibility split

HAI concepts must explain these meanings and their relationships in plain language:

| Entity | Responsibility and owned content |
| --- | --- |
| AI agent | The executing tool or running worker that performs an assignment. |
| Role | A job description: responsibilities, scope, professional perspective, expected quality, decision limits and handoff obligations; references the skills it uses. |
| Skill | A reusable capability: task instructions, internal procedures, supporting scripts, templates and task-specific knowledge or conventions. |
| Workflow | A reusable process: step assignments, responsible roles, dependencies, input/output contracts, named results, selection conditions and next steps. |
| Activity | The boundary and retained records for actual work, including workflow runs. |

The following principles come from the preceding discussion and must be retained
in the design. Their exact representation and mechanisms remain to be reviewed:

- A role defines responsibility under the user's actual authorization. Selecting
  a role or skill does not grant additional permissions or launch an AI agent.
- Several roles can reuse one skill. A role references a skill rather than copying
  its method, scripts and templates into its own package. A person can also use
  a skill directly without selecting a HAI role, within the authorized task scope.
- A role can retain genuinely role-specific conduct, knowledge, conventions,
  procedures or helpers when they support a responsibility across its skills.
  Identical folder trees and empty configuration contracts at both levels are
  not requirements of this item.
- A skill owns the reusable method for a task. Not every small internal procedure
  must become a separately packaged skill; extraction must yield coherent capabilities.
- A workflow step states what to accomplish for that process, with its input and
  output expectations without copying detailed skill instructions. Workflow steps
  name the responsible role and expected result; the assigned role selects suitable
  available skills. The workflow does not prescribe a skill binding. If no suitable
  skill is available, the assignment reports the dependency and does not claim success.
- Shared project/framework conventions and shared data contracts have one owner;
  roles, skills and workflows reference them rather than create conflicting copies.
- Settings belong to the capability, service or role that actually owns them and
  are stored once. Workflow output-location settings configure a process instance
  for an environment; they do not duplicate unrelated integration settings.
- Reusable definitions do not contain execution status or generated run outputs.
  Runtime records, accepted results and evidence remain with their execution.

### 2. Reusable source collections

The repository must use the following source layout:

```text
roles/
  backlog-manager/
    ROLE.md
  business-analyst/
    ROLE.md
  ...other role folders directly...
skills/
  <skill-name>/
    SKILL.md
    ...resources needed by this skill...
workflows/
  software-development.md
```

- Rename and flatten `hai_roles_library/roles/` into root `roles/`. The result must
  not contain a second `roles/` directory between the collection and role packages.
- Reuse the existing root `skills/` collection and preserve its existing skills.
  Extract the reusable capabilities currently embedded in role packages into
  separate skills there, and update roles to reference them.
- Create a root `workflows/` source collection with one initial software-development
  workflow. `software-development.md` is the proposed descriptive filename.
- Keep source collections distinct from installed environment packages. The item
  does not request a second rename of the existing `.hai_env/roles/` root.
- Adapt affected relative links, imports, validators, installation/registration,
  migration paths, documentation and relevant checks. Flattening changes the
  relative depth of role packages and must not leave broken core/peer references.
- Preserve installed customizations, settings, existing skills and historical
  records. The design must explain migration and dependency handling before apply.

### 3. Initial software-development workflow

The initial workflow must include these five roles:

1. Backlog-manager.
2. Business-analyst.
3. Solution-architect.
4. Software-developer.
5. Quality-assurance.

The normal process uses the following responsibilities. Concrete filename stems
below are illustrative; the naming pattern is agreed, while the workflow author
must declare the exact intermediate and final artifact names.

| Assignment | Role | Illustrative intermediate filename pattern |
| --- | --- | --- |
| Prepare the selected backlog work and known constraints | Backlog-manager | prepare-{attempt}-work-item.md |
| Clarify the request and define requirements/acceptance criteria | Business-analyst | clarify-{attempt}-requirements.md |
| Design the solution and prepare implementation/verification guidance | Solution-architect | design-{attempt}-solution-design.md |
| Implement the approved design and perform developer checks | Software-developer | implement-{attempt}-implementation-report.md, plus declared product changes |
| Verify the result against acceptance criteria and report findings | Quality-assurance | verify-{attempt}-verification-report.md, plus defect evidence when applicable |
| After QA passes and the human accepts the result, record backlog completion and evidence | Backlog-manager again | Declared completion evidence and updated backlog item |

The last assignment reuses Backlog-manager; it does not introduce a sixth role.
The role may appear in more than one workflow step. Workflow steps name roles
and expected results, while the assigned roles select their skills.

The workflow must define its single entry step, step instructions, required
inputs, expected outputs and meaningful completion criteria. It must define the
recognized result names and their evidence, with explicit next steps or endings
for success, failure and other authored conditions. The existing model permits
any number of named results; this item does not reduce it to success/failure only.
The workflow must identify which accepted outputs each downstream step consumes.
QA rework and other return paths must be explicit and use bounded attempts under
the existing loop principles. On a partial return, every required input must retain
an explicit binding to its accepted source: a newly accepted result where applicable
and the still-applicable earlier requirements, approved design and other evidence
where those steps were not repeated. Missing, changed, unaccepted or superseded
required inputs block dependent acceptance until the host resolves them. A stale
approval cannot be reused for materially changed scope or design.

The initial workflow must wait for human approval before implementation begins
and before the backlog item is marked completed. QA success alone does not equal
human acceptance. Approval must correspond to the current agreed scope/design;
material changes cannot rely on stale approval. After QA success and human
acceptance, the workflow must return to Backlog-manager to record completion
and its supporting evidence. It must not close the Activity automatically.

### 3a. Run, loop and intermediate naming

- Each workflow run must have its own folder within each configured output base.
  Configured folders are base destinations rather than one shared overwrite target.
- Every intermediate filename must identify its step and that step's execution
  number. HAI must assign the execution number, not ask an AI agent to invent it.
- HAI must count executions separately for each step, including repeat attempts
  caused by loops or retries. A global whole-loop number is not sufficient because
  a branch can repeat some steps without repeating the others.
- A repeat attempt must create distinguishable artifacts and preserve earlier
  attempts. Downstream steps must receive the exact accepted predecessor paths;
  HAI must not infer inputs from filenames that merely appear to be the latest.
- The workflow defines the filename pattern and artifact names. The environment
  configuration supplies base locations, and HAI resolves the run folder and
  execution number. The illustration uses {attempt} for that number; exact syntax,
  padding and run-folder identifiers are design details.

For example, a return from design to clarification may produce:

```text
<configured-base>/<run-folder>/
  clarify-001-requirements.md
  design-001-solution-design.md
  clarify-002-requirements.md
  design-002-solution-design.md
```

The illustration does not require every step to execute twice. A second design
step must consume the explicitly accepted second clarification output if that is
the predecessor selected by the process, rather than the first requirements file.

Final published outputs may retain stable names separately from intermediate
attempts. The workflow must declare which artifacts are final outputs. The design
must explain the publication/update behavior and preserve recorded intermediate
versions. Stable names do not authorize destructive replacement or publication
beyond the user's actual task scope.

The workflow stays within one Activity. Several runs may belong to an Activity,
but only one may execute at a time. The owning Activity retains authoritative
accepted attempt evidence, immutable initial snapshots, input identities and lineage,
so that accepted evidence and its integrity remain inspectable after later attempts
and Activity archival. Configured destinations provide locations for the outputs
and handoffs required by the workflow; they do not transfer ownership of run
records or make an external copy alone the authoritative accepted evidence. Durable
product outputs retain their existing canonical ownership and locations. The design
may choose how accepted evidence and configured artifacts are related, provided
these outcomes and the accepted predecessor identity are preserved.

### 4. Environment-specific workflow configuration and installation

The workflow concept and its dependent contracts/runtime must support installation
of a reusable workflow with custom configuration for the target environment.

- During workflow installation, HAI must ask the human for the required locations.
  HAI must explain the purpose of each location and the outputs it will contain.
- The environment configuration must define locations for the relevant outputs
  of each step and each authored result, including intermediate handoff artifacts
  and final outputs. Several artifacts may share a folder when their contracts
  allow it; a separate setting per file is not imposed by this item.
- Every configured location must be a path relative to the workspace root. Path
  meaning must not depend on the invoking shell's current directory or source
  package location. HAI must reject escaping or otherwise unsafe locations.
- The workflow definition owns artifact names, intermediate filename patterns and
  output contracts. The environment configuration supplies destination bases. HAI
  must combine them with the run folder and step execution number to resolve
  unambiguous workspace-relative paths under the agreed isolation rules.
- Each consuming step must receive the resolved locations of its declared inputs
  from predecessor outputs. HAI must check required files before dependent work;
  matching labels alone must not imply a handoff or prove content quality.
- Missing required locations must be resolved with the human before the installed
  workflow is treated as ready to execute. Installation does not itself start a run.
- Configuration values must survive ordinary reuse of the installed workflow.
  Updating a definition must not silently discard chosen environment locations.
- Each accepted handoff must be traceable to the producing run, step and attempt,
  including its accepted content identity and the exact input bindings consumed.
  Earlier accepted evidence stays inspectable after rework and archival. Required
  files and their accepted identity are checked before dependent work; the host
  assesses meaning and acceptance, rather than treating file presence as quality.

The configuration file format/location, installation commands and the mechanism
for resolving skills available to a role are design decisions still to be reviewed.
The behavioral decision is settled: workflow steps do not prescribe skills.
No particular new configuration filename or workflow schema is approved here.

### 5. Confirmed clarification and remaining design work

The human answered Q001-Q005 during clarification and accepted continuing after
the loop-naming proposal. The effective requirements are:

1. Runs use separate folders, and intermediate names distinguish executions of
   each step, including repeats within the same run.
2. Skills can be used directly or through roles within actual task authority.
3. Workflow steps specify roles and expected results; roles select skills.
4. The initial workflow waits for approval before implementation and before
   backlog completion.
5. After QA success and human acceptance, Backlog-manager records completion
   without automatically closing the Activity.

The design must still explain implementation choices without reopening those
requirements:

- How configured workspace-relative destinations coexist with Activity-owned
  run/attempt state, snapshots and evidence; distinguish intermediate handoffs,
  durable product outputs and runtime records.
- The filename-pattern syntax, run-folder identity, execution-number formatting,
  exact input-path binding, and stable final-output publication/update behavior.
- The inventory and grouping of skills extracted from current roles, role-specific
  resources, shared contract ownership, and skill installation/resolution.
- The initial workflow's exact result conditions, QA rework routes and declared
  file contents, using the agreed roles, human checkpoints and completion handoff.
- Migration of source/installed packages, local customizations, settings and
  existing reusable workflows while preserving historical evidence.

These are delivery-design topics rather than unanswered choices about the five
clarified behaviors. The human has not authorized implementation or accepted a
technical design by answering the clarification questions.

### 6. Participants, exclusions and constraints

HAI users/operators need predictable handoffs and output locations. Role/skill
and workflow authors need clear ownership without duplicated methods; framework
maintainers need consistent installation, validation and migration behavior.
This work follows the human-selected role/skill discussion; no deadline or urgent
priority ranking has been specified.

The scope is the existing HAI framework and the requested initial development
workflow. Additional business workflow examples, a GUI, cross-workspace paths,
automatic Activity closure, remote publication and unrelated source-format
repairs are excluded. Configured artifact paths must remain workspace-relative.
Existing workspace containment, source/installed separation, truthful evidence,
permission boundaries and historical-preservation rules continue to apply.

The item is an umbrella for a coordinated framework change. Its bounded delivery
outcomes are listed below without assigning priorities or removing any requested
scope. Each outcome must be independently reviewable and have the acceptance
evidence specified below; delivery can be sequenced after authorized analysis.

1. **Responsibility and source foundations:** document concepts and ownership,
   flatten the role source collection, preserve and adapt affected references, and
   retain existing skills and historical records (AC1–AC2, AC9).
2. **Reusable skills and roles:** inventory current role capabilities, extract
   coherent reusable skills, retain justified role-specific material, make them
   usable directly and through roles, and preserve installed customizations and
   settings (AC3, AC9, AC11). Depends on the agreed responsibility boundaries.
3. **Configurable workflows and retained handoffs:** support installation-time
   environment locations, safe reusable configuration, run isolation, accepted
   evidence and explicit input lineage across partial returns (AC5–AC9). Depends
   on the agreed output ownership and existing Activity retention rules.
4. **Initial development workflow and integration:** define and verify the five-role
   workflow, its bounded routes, human checkpoints and completion handoff using the
   above capabilities (AC4–AC8, AC11–AC13). Depends on the usable role/skill and
   workflow contracts; the integrated result must satisfy all criteria together.

A reviewed design must refine implementable increments and dependencies without
changing these outcomes. This does not claim an estimate or authorize execution.

Preservation and compatibility are constraints: existing installed customizations,
settings, skills and historical evidence must remain available and attributable.
If a safe migration or compatibility cannot be established, the affected update must
stop, preserve the pre-existing material and report what needs a decision. No
incompatible or destructive migration is inferred from this item; any such change
requires separate actual human authorization.

## Why

Give roles, skills and workflows distinct purposes so reusable methods can be
shared without duplicating instructions, scripts, conventions and settings.
Make the source layout simpler and make a standard software-development process
portable between environments with different output destinations.
